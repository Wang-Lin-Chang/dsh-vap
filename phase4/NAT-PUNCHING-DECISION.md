# NAT 打洞 / libp2p / 中继 —— 三方案决策（质疑零依赖教条）

> 立项问题：跨 NAT 这一步，零依赖是纪律还是教条？
> 结论：**零依赖是强默认，不是教条——打破它需要数据，不是冲动。**
> 本阶段用「中继模式全自研 + 本决策文档有根据」来回答。

## 1. 三方案对比

| 方案 | 论点 | 代价 |
|---|---|---|
| **自研 STUN 打洞** | 零依赖纪律延续；锥型 NAT 上基本打洞可行（RFC 5389 不复杂） | 对称 NAT/CGNAT 失败率真实存在（10-30%）；打洞 + 保活 + 重绑定是长尾工程 |
| **引入 libp2p** | DCUtR / circuit-relay / AutoNAT 被 IPFS + 以太坊 2.0 真实流量磨过 | 供应链：审计不了 libp2p 全部代码；依赖体积大；PeerID 身份映射（MAJOR-5 已定规范） |
| **中继优先（本阶段）** | 零依赖、已实现、跨 NAT 通信立即成立 | 延迟/带宽成本；中继是中心化点（诚实标注信任边界） |

## 2. 决策

**中继模式先行（本阶段实现）**；打洞决策留到「无激励基线数据」出来后：

- 若单机中继可服务规模够信任域用 → 打洞优先级降低；
- 若不够 → 再启动自研 STUN 或引入 libp2p 的评估。

判定入口是数据（R4 无激励基线的承载力数字），不是偏好。

## 3. 为什么零依赖在这里仍是强默认

1. **vap-core 的三闸安全边界不依赖第三方密码库**：Ed25519 用 node:crypto，信封/验签/军法/诚实边界全部自研可审计。
2. **中继模式零依赖已让跨 NAT 通信成立**：先跑通功能，再谈优化，符合本仓库一贯的「文件即消息、逐步迭代」节奏。
3. **引入依赖的成本是审计义务**：libp2p 体积大、协议多，本阶段无审计能力，引入即把未审计代码放进信任边界。

## 4. 什么时候打破（触发条件，非教条）

满足任一条件即重启打洞/libp2p 评估：

- R4 无激励基线显示单机中继承载力不足信任域规模（例如并发连接或字节转发率撞墙）；
- 出现必须低延迟、去中心化拓扑的硬需求（中继延迟/单点不可接受）；
- 真实跨 NAT 实测（公网环境）测出锥型 NAT 占比高、自研打洞可行且失败率可接受。

## 5. 本阶段的诚实边界

- 中继是中心化点：只见明文、不可伪造（验签必败）、可选择性丢弃——信任边界 = 「不可信但不可作恶」，作恶（审查/丢包）可被检测（R3），但不可防止。
- 打洞未做，libp2p 未引入，本决策文档是「有根据的搁置」而非「未想清楚」。

## 6. 结论一句话

> 零依赖是强默认：能用 node: 内置模块把跨 NAT 通信做成立，就先不做打洞、不引入 libp2p；等 R4 数据证明不够用时，再依据数据决定是否打破默认。
